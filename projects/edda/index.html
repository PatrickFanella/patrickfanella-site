Edda

An LLM-powered dungeon master application in Go that serves both a terminal UI and REST API from the same game logic.

Status
Status not stated in source
Role
Application engineer

2026
Visit Edda Repository

Product and scope

Edda runs an LLM-powered game master through either a terminal UI or REST API. The cmd/tui and cmd/server entry points share game logic from internal packages, while pkg/api exports integration types. Koanf reads YAML and GM_ environment variables, goose manages database migrations, and Docker Compose runs the local stack.

Stack
Go, TUI, REST API, LLM, PostgreSQL, Docker, Goose

The problem

A game master needs an interactive interface, while integrations need an API. Both should use the same rules and state instead of duplicating game logic.

What I built

  • Built a Go application that serves both a terminal game-master experience and a REST API from the same codebase.
  • Structured the project around cmd/tui and cmd/server entry points, internal packages, and exported pkg/api types for external integration.
  • Added YAML and GM_-prefixed env configuration, goose migrations, and Docker Compose support for repeatable local deployment.

How it fits together

Go runtime splits into TUI and server entry points so interactive play and API access share the same game logic.

Koanf layers YAML and GM_ environment variables into one config surface, while goose manages schema changes for the Postgres-backed game state.

Docker Compose provides a reproducible local stack for the app, API, and database.

What I learned

  • People want a terminal and integrations want an API. Separate entry points over shared game logic serve both without duplicating the rules.
  • Boring infrastructure helped. With explicit migrations, layered config and repeatable containers, the model was one of the few moving parts left to debug.
