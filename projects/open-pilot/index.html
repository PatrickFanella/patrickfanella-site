Open Pilot

A self-hosted automation service that turns approved Gitea issues into tested pull requests through OpenCode-driven code changes in isolated worktrees.

Status
Status not stated in source
Role
Automation engineer
Period
2026

Product and scope

Open Pilot turns approved Gitea issues into OpenCode jobs. A webhook adds ready issues to a durable queue. One worker claims each job, creates a git worktree, edits the code, runs tests, and pushes a branch for a pull request. Logging, a dashboard, a scheduler, and supervisor helpers are available, but the optional services stay disabled by default.

Stack
Python, Gitea, OpenCode, Webhooks, SQLite, Agents, Automation

The problem

Issue-driven code automation can change and push a repository, so operators need a clear approval boundary, isolated worktrees, test results, and durable job logs.

What I built

  • Built the issue-to-PR runner that receives ready issue webhooks, claims jobs from a durable queue, and drives OpenCode changes inside a git worktree.
  • Added conservative self-hosted defaults with FIFO ordering, a single worker, and dashboard and scheduler features disabled unless explicitly turned on.
  • Integrated test execution, branch pushing, logging and helper services around that runner.

How it fits together

Webhook receiver accepts ready issue events from Gitea and places them into a durable queue backed by SQLite.

A single worker claims queued jobs, uses OpenCode in a dedicated worktree, runs tests, and pushes the result as a branch or pull request.

Dashboard, scheduler, supervisor and autopilot helpers exist but stay opt-in. The default install is a small MVP for a trusted, self-hosted setup.

What I learned

  • Trusted automation still needs conservative defaults; FIFO scheduling and one-worker execution make the first self-hosted deployment easier to reason about.
  • In an issue-to-PR system, policy, logs, tests and worktree isolation are the product, and I treat them that way.
