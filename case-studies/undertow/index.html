Undertow

A video rendering pipeline inside the browser

Undertow gives a musician a way to turn a track, artwork and timed lyrics into a video. The editor is only the beginning: the same project has to produce frames, encode them and finish a playable file within the browser’s limits.

Treat the export as part of the editor

A preview can look right while the exported file has the wrong timing, no audio or an allocation failure. The editor therefore needs a real rendering pipeline, not a screen recording of the preview.

I built the React editor, layered compositor and local export path. Projects keep separate landscape, portrait and square layouts. Visuals can react to audio, and timed lyrics can sit alongside artwork, text and video layers.

  • Editor and export capabilities

Keep frame production and encoding explicit

The export loop analyzes, draws and encodes frames through MediaBunny and the browser’s codec APIs. It negotiates an encodable video and audio format instead of assuming every browser supports the same combination.

Encoder promises do not necessarily yield control back to the page. The pipeline explicitly yields a macrotask, and the frame-capture path handles GPU/CPU copying with a pixel-readback fallback.

The tradeoff. Local rendering keeps media on the user’s device, but codec availability and encoding speed depend on that browser and hardware. A supported resolution is not a promise that every device can encode it.

Let the muxer seek without one giant buffer

Video containers need to patch metadata written earlier in the file. Undertow’s BlobChunks output maps writes into seekable chunks so the muxer can revise headers without allocating an ArrayBuffer as large as the finished video.

The regression test first constrains individual ArrayBuffer allocations, demonstrates the original in-memory path failing, then exports and demuxes a larger file through the chunked path. Another check verifies bytes when a header write crosses a chunk boundary.

The tradeoff. Chunking avoids a single large contiguous allocation. It does not make output storage free or remove the device’s overall memory limit.

Separate the local product from optional services

The public editor works without an account. Optional accounts and cloud rendering are a separate capability in testing, and live paid billing is off. They are not needed to explain the local rendering work.

The screenshots use an isolated demonstration project, an original eight-second synthesized track and the portfolio’s approved PF artwork. They show the real editor and export controls, not a client commission or a measured encoding benchmark. The repository also provides a browser self-test that encodes and reads actual output files.

Evidence and limits

Encoding support, audio output and achievable resolutions vary by browser and hardware. The captured demonstration does not qualify every device or the optional cloud-rendering service.
