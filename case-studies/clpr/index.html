Clpr

Making Twitch clips discoverable

A clip can outlive the stream that made it interesting, but finding it again requires more than a list sorted by views. Clpr connects creators, topics and tags to a searchable clip library, then gives people collections and playlists for the things they want to keep.

Start with the way people look for a clip

A reader might remember a creator, a topic, a line of speech or only part of a title. The product needs to support those different starting points and let browsing remain useful when there is no precise query.

I built the Go API, React client and search pipeline, together with the account, submission and moderation workflows around them. The current public collections view makes the product legible before a reader learns anything about its backend.

  • Current product scope

Give each search result a clear contract

The Go repository builds independent clip, creator, game and tag result sets. A request selects the relevant branches, and each branch returns its own result count. That keeps the response meaningful for a broad search as well as a clip-only view.

The active search path also supports a speech-transcript filter. Validation treats a phrase-only search as a clip request and rejects empty or oversized input. These are product semantics that the API tests can name directly.

The tradeoff. Counts, filtering and ordering are part of the interface contract. Changing a query to make it cheaper can also change navigation or what the reader thinks matched.

Keep the supported product smaller than the repository

An implementation can exist in a repository without belonging to a supported release. Clpr’s launch inventory explicitly removes or disables features that have not met their promotion gates. Current discovery, playlists and moderation are the story I present here.

The inventory also makes the maintenance boundary concrete: retired forums, watch parties and billing are not advertised as present-day capabilities. Automated account deletion and full data-subject export remain outside the supported launch contract.

The tradeoff. A smaller supported surface means saying exactly what is available. Historical code is useful context, but it is not evidence that a capability shipped.

  • Release-scope contract

Make the implementation inspectable

The source walkthrough explains ranking, filtered counts, transcript snippets and numbered pages in a pinned PostgreSQL implementation. The engineering Desk takes that further: an opt-in worker runs the pinned Go path against labelled fixture clips and exposes SQL, timings, protocol messages and plans.

Those artifacts explain a particular version of the search code. They do not establish the current production backend, traffic, relevance quality or a universal speedup. The new screenshots show the public discovery interface as it appeared on November 16, 2026.

Evidence and limits

This study combines current public product documentation with an explicitly versioned code demonstration. Fixture timings are not production latency or traffic measurements.
